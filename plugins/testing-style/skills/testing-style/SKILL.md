テストを書くときの指針。特定の言語に依存しないルール群。言語やテストランナーに固有の規則は、次に示す言語別スキルに記載している。併用すること。

| テストランナー    | スキル名                              |
| ----------------- | ------------------------------------- |
| Vitest            | `testing-style:testing-style-vitest`  |

これらに記載のない事柄はコードベースの既存テストに合わせること。

## 規則

### テスト対象を選ぶ

自分で書いたロジックを含むコードはすべてテスト対象とする。ロジックとは分岐、変換、計算を指す。

外部ライブラリーやフレームワークの公式 API の動作確認にしかならないテストは書かない。そのライブラリーが検証済みの内容を重ねて確かめても、意味がないため。

- 引数をそのまま公式 API に渡すだけのコードはテスト対象外とする
- 公式 API を呼ぶコードでも、渡す値を組み立てていればテスト対象とする
- モジュール外に公開していない関数もテスト対象とする
    - in-source testing で書くため、公開せず同じファイルから直接テストできる
- ログ出力の整形など、人間が読む出力を組み立てるだけのコードはテスト対象外とする
    - 表示のための文字列であり、仕様として検証する対象でないため
- テストを書かないと判断した場合、その理由をテストブロック冒頭にコメントで書く

### テスト技法でケースを導出する

テスト対象ごとに、入力と前提状態から考えうるパターンを網羅する。テストケースは思いつきで選ばず、次のテスト技法で導出する。技法にはカバレッジ基準があり、網羅できたかを判断できるため。

| 技法 | 適用する場面 |
| --- | --- |
| 同値分割 | すべての入力に適用し、各同値クラスから 1 ケースを書く |
| 境界値分析 | 範囲や長さに制約のある入力に適用し、境界の両側を書く |
| デシジョンテーブル | 複数の条件の組み合わせで動作が決まるロジックに適用する |
| 状態遷移テスト | 状態を持つ対象に適用し、すべての遷移と無効な遷移を書く |
| ペアワイズ | まずテスト対象を分割して組み合わせを減らし、それでも組み合わせ自体が仕様として残る場合に適用する |
| プロパティベーステスト | 入力の全域で成り立つ性質を書ける純粋関数に適用する |
| エラー推測 | 上記の技法で導出したケースを、経験に基づいて補う |

技法を適用してもケースが多すぎる場合はテストを削らず、テスト対象を分割する。分割すると各テスト対象のパターン数は積でなく和になる。

網羅は各テスト対象の中で閉じる。依存を取りまとめる層では、依存を正しく呼べていることを確かめる。依存の内部のパターンとの組み合わせは書かない。

### テストサイズを small に保つ

テストサイズは実行時に使ってよいリソースの範囲を表す。範囲が広いほど実行が遅く、結果が不安定になり、失敗時の原因特定に時間がかかるため、テストサイズは極力小さくする。この区分は [Google のテストサイズ定義](https://testing.googleblog.com/2010/12/test-sizes.html)に準拠する。

| サイズ | 使ってよいリソース |
| --- | --- |
| small | 単一プロセス内のみ<br>sleep、I/O、ブロッキング処理を使わない |
| medium | 単一マシン内のみ<br>複数プロセス、localhost へのネットワークアクセスを使える |
| large | 上記の制限を受けない<br>別マシンへのアクセスを使える |

サイズを 1 段上げるときは、下のサイズで書けない理由をテストのコメントに書く。

対象を small に保てない設計は、テストではなく対象コードの依存関係を見直すべき兆候として捉える。現在時刻や乱数の取得など外部への依存は、直接記述せず引数やインターフェイス越しに受け取る形にする。

### テストスイートでまとめる

テストケースは、対象となる関数やモジュール、前提状態の単位でくくり、テストスイートとしてまとめる。読み手はスイート名から対象を特定でき、失敗したテストの範囲をすぐ絞り込める。また多くのテストランナーは特定のスイートだけを実行する機能を持つため、開発中のテスト実行時間を抑えられる。

- スイート名には対象の名前や前提状態をそのまま書く
- 同じ対象のテストを複数のスイートに散らさない
- テストケース名は確かめたいことを端的に書く

### テストケース名の決め方

次を含め、端的に書く。

1. テスト対象をどう操作したか？
    - 関数を呼び出す
    - 特定の値を入力する
2. 期待する結果
    - 意味のない期待値は書かないこと
        - 正しく動く
        - 値を返す

前提条件はテストケース名に含めない。テストスイート名に置く。

### 用語

テストスイート名、テストケース名とも Design Doc や ADR などドキュメントに記載されている言葉を用いる。テストは仕様の verification という側面を持つため。ドキュメントがない場合はコードベースの既存の用語にあわせる。

### in-source testing で書く

テストは対象コードと同じファイルに書く。離れた場所にあると対象とテストの対応を確認する手間がかかる。また、対象とテストが同じ場所にあるとテストの更新漏れに気づきやすい。

- テストは対象コードと同じファイルの末尾にまとめる
- テストコードが製品ビルドに含まれないようにする
- 複数モジュールをまたぐ integration test と E2E test は対象外とする
    - 言語やフレームワークの標準的な配置に従う
- モックは直接依存しているものに限る
    - 依存の依存を推移的にモックしない
- in-source testing をサポートしない言語やテストランナーでは、その標準的な配置に従う

## 手順

1. 規則に従ってテストを書く
2. Agent ツールで `skill-adherence:skill-adherence-checker` sub-agent を起動し規則違反をチェックさせる
    - この sub-agent が使えない環境ではこの検査を省く
    - 次を渡す
        - `testing-style:testing-style`
        - 変更したファイルのパス
3. 報告された違反を修正する
    - 修正がさらに規則に違反していないか注意する
