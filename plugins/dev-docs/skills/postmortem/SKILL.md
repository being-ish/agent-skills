# postmortem の生成と更新

postmortem は起きた障害の事後分析を記載する。

## ドキュメント間の関係

各ドキュメントは、表で自分より上にあるドキュメントを前提として書く。

| ドキュメント | 書くもの |
|---|---|
| PRD | 要件、制約、スコープ |
| ADR | 決定とその理由 |
| design doc | 実現方法、現時点の設計 |
| runbook | 運用作業の手順 |
| postmortem | 起きた障害の事後分析 |

- 他のドキュメント種別に属する内容は書かない
    - 対応手順そのものは書かず、runbook へリンクする
    - 設計の背景や理由は書かず、design doc / ADR へリンクする
- リンクは表で自分より上にあるドキュメントへだけ張る
    - 逆方向へは張らない
    - 同じ種別どうしのリンクは張ってよい

## feature とは

Screaming Architecture における機能の凝集単位。
フロントエンドからバックエンドまでを横断する、機能で切った単位を指す。
システム横断のドキュメントは、特定の feature に閉じない内容を扱う。

## 出力先

- システム全体: `/docs/postmortems/` 以下
- feature 固有: `/docs/features/<feature-name>/postmortems/` 以下

`/docs/features/` が存在しないリポジトリーでは、出力先をユーザーに確認する。

1 ファイルに 1 件の障害を書く。
ファイル名は `YYYY-MM-DD-kebab-case-title.md` の形式とし、日付は障害の発生日とする。

## テンプレート

`${CLAUDE_SKILL_DIR}/references/postmortem.md` を使う。

## 規則

- 個人を非難しない
    - 人ではなく、その判断を引き起こした仕組みや情報の不足を原因として書く
    - 「誰が間違えたか」ではなく「なぜその判断が妥当に見えたか」を書く
- 事実と判断を分けて書く
    - 事実の節には観測できた事象と実施した操作を書く
        - 事後分析に必要な推定だけを、根拠とともに推定と明記して書く
            - 必要でない推定は書かない
    - 分析、評価、対策の提案は判断の節に書く
        - 分析で確認できていない事柄は推測であると明記する
- アクションアイテムは実行できる粒度まで具体化する
- アジリティを落とさない
    - 日常の作業を増やすルールや仕組みは検討外とする
    - 注意や運用ルールに頼らず、自動化やデフォルトを安全に倒すなど仕組みで防ぐ
    - 全防止策の効果が費用と時間に見合わなければリスク受容と書いて終える
- 影響は PRD の要件や SLO の定義を参照して書き、定義のない指標を新たに作らない
- タイムラインの時刻はタイムゾーンを明記する
- 根本原因は「なぜ」を繰り返し、仕組みの問題に到達するまで掘り下げる
    - 途中の「なぜ」と答えも省略せずに書き、思考の過程を残す
- 情報が不足しているセクションは「TBD」と記載する
- 関連ドキュメントは本文の該当語句にインラインリンクを張る
- 現在の実装状況を判断に使わず、ドキュメントに実装状況を書かない
    - 障害発生時点の挙動や設定は事実として書く
- テンプレートのセクション構成に従う

## 手順

1. 生成 / 更新対象の postmortem がシステム全体か feature 固有かを判断する
    - 単一の feature に閉じる障害なら feature 固有、複数 feature やシステム基盤に関わるならシステム全体とする
    - `/docs/features/` 以下のディレクトリー一覧を feature の候補として参照する
    - 不明ならユーザーに確認する
2. テンプレートを読み込む
3. 出力先ディレクトリーの既存 postmortem を確認する
    - 更新なら該当ファイルを読み込み、更新対象とする
    - 新規なら同じ障害を扱う既存 postmortem がないかを確認する
4. ユーザーの要求と既存情報をもとに、規則に従って postmortem を作成、更新する
    - 障害対応時のログ、アラート、Issue、Pull Request を情報源として参照する
    - 「TBD」と記載したセクションはユーザーに確認する
5. 該当する障害の incident runbook の有無と、今回の対応内容との差異を確認して報告する
    - この場では runbook の作成、更新をしない
    - 原因の理解が防止策を左右するため、runbook の整備は postmortem を人間がレビューした後に別途行う
6. PRD や design doc、ADR など関連ドキュメントが存在する場合、整合性をチェックし、矛盾があればユーザーに報告する
7. plan-tasks スキルで作成したタスクリスト Artifact が本作業に存在する場合、postmortem の変更に伴う更新が必要かを確認し、必要であれば更新する
8. GitHub Issues を確認し、アクションアイテムに対応する Issues の追加、変更、削除が必要であればユーザーに進言する
9. 出力先に postmortem を書き出す
10. Task ツールで `skill-adherence:skill-adherence-checker` sub-agent を起動し、`dev-docs:postmortem` と書き出したファイルのパスを渡して Skill 違反を検査させる
    - この sub-agent が使えない環境ではこの手順を省く
    - 報告された違反を postmortem に反映する
